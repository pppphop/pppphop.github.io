6 = 4 FN (假阴性) = 真实P - TP = 8 - 6 = 2 TN (真阴性) = 真实N - FP = 32 - 4 = 28 计算指标： 查准率 (Precision) = $TP / (TP + FP) = 6 / 10 = \mathbf{60%}$ 查全率 (Recall) = $TP / (TP + FN) = 6 / 8 = \mathbf{75%}$ F1 值 = $\frac{2 \times P \times R}{P + R} = \frac{2 \times 0.6 \times 0.75}{0.6 + 0.75} = \frac{0.9}{1.35} = \mathbf{66.7%}$ (或 $\frac{2}{3}$) (2) k折交叉验证流程 将数据集 $D$ 随机划分为 $k$ 个大小相似的互斥子集。 每次用其中的 $k-1$ 个子集作为训练集，剩下 $1$ 个子集作为测试集，进行模型的训练和评估。 循环上述过程 $k$ 次，使得每个子集都刚好被当作一次测试集。 将这 $k$ 次测试结果的平均值作为该模型最终的性能评估。 第二题：贝叶斯决策理论已知条件汇总： 先验概率：$P(\omega_1) = 0.8$, $P(\omega_2) = 0.2$ 类条件概率（似然）：$P(x|\omega_1) = 0.25$, $P(x|\omega_2) = 0.5$ (1) 最小错误率决策根据贝叶斯公式，后验概率 $P(\omega_i|x) = \frac{P(x|\omega_i)P(\omega_i)}{P(x)}$。因为全概率 $P(x)$ 对所有类别相同，所以只需比较分子 $P(x|\omega_i)P(\omega_i)$ 的大小： 对于 $\omega_1$（无事故）：$P(x|\omega_1)P(\omega_1) = 0.25 \times 0.8 = \mathbf{0.20}$ 对于 $\omega_2$（发生事故）：$P(x|\omega_2)P(\omega_2) = 0.5 \times 0.2 = \mathbf{0.10}$ 因为 $0.20 > 0.10$（即 $P(\omega_1|x) > P(\omega_2|x)$），为了使错误率最小，应判定为 $\omega_1$（无事故）。 (2) 最小风险决策首先，计算真实的后验概率。全概率 $P(x) = 0.20 + 0.10 = 0.30$。 $P(\omega_1|x) = \frac{0.20}{0.30} = \mathbf{\frac{2}{3}}$ $P(\omega_2|x) = \frac{0.10}{0.30} = \mathbf{\frac{1}{3}}$ 接下来，根据给定的代价矩阵计算采取两种决策的条件风险： 判定为 $\omega_1$ 的风险 $R(\alpha_1|x)$： $R(\alpha_1|x) = \lambda_{11}P(\omega_1|x) + \lambda_{12}P(\omega_2|x) = 0 \times \frac{2}{3} + 6 \times \frac{1}{3} = \mathbf{2}$ 判定为 $\omega_2$ 的风险 $R(\alpha_2|x)$： $R(\alpha_2|x) = \lambda_{21}P(\omega_1|x) + \lambda_{22}P(\omega_2|x) = 1 \times \frac{2}{3} + 0 \times \frac{1}{3} = \mathbf{\frac{2}{3}}$ 因为 $R(\alpha_2|x) < R(\alpha_1|x)$ （即 $\frac{2}{3} < 2$），为了使风险最小，应判定为 $\omega_2$（发生事故）。 第三题：线性模型与感知机更新规则：若 $y_i(w^Tx_i + b) \le 0$，则 $w \leftarrow w + \eta y_ix_i$，$b \leftarrow b + \eta y_i$。初始 $w=(0,0)^T, b=0, \eta=1$。 第一轮迭代： 考查 $x_1(2,1)$ [正类]: $1 \times 0 \le 0$，错分。更新：$w = (2,1)^T, b = 1$ 考查 $x_2(3,2)$ [正类]: $1 \times (6+2+1) = 9 > 0$，正确。 考查 $x_3(-1,1)$ [负类]: $-1 \times (-2+1+1) = 0 \le 0$，错分。更新：$w=(2,1)^T - (-1,1)^T = (3,0)^T, b = 1-1 = 0$ 考查 $x_4(0,0)$ [负类]: $-1 \times (0+0) = 0 \le 0$，错分。更新：$w=(3,0)^T - (0,0)^T = (3,0)^T, b = 0-1 = -1$ 第二轮迭代： $x_1$: $1 \times (6-1) = 5 > 0$ $x_2$: $1 \times (9-1) = 8 > 0$ $x_3$: $-1 \times (-3-1) = 4 > 0$ $x_4$: $-1 \times (0-1) = 1 > 0$全部正确，算法收敛停机。 最终决策函数： $f(x) = \text{sign}(3x^{(1)} - 1)$ 第四题：支持向量机 (SVM)(1) 基本原理：SVM 试图在特征空间中寻找一个能够将两类样本正确分离，且使得分类间隔（Margin）最大化的超平面。最大化间隔可以使得模型对未知数据具有更强的鲁棒性，从而提升泛化能力。(2) 处理不可分与噪声： 线性不可分问题： 引入核技巧（Kernel Trick），将低维空间线性不可分的数据隐式地映射到高维特征空间，使其变得线性可分。 噪声问题： 引入软间隔（Soft Margin），即加入松弛变量 $\xi$ 和惩罚参数 $C$，允许个别噪点越过间隔边界，防止模型为了拟合噪声而产生过拟合。 第五题：决策树 (ID3算法)(1) 基本原理：决策树采用自顶向下的递归划分策略。ID3算法的核心准则是信息增益（Information Gain），即每次在节点分裂时，选择能使得数据集纯度提升最大（信息熵下降最多）的特征进行划分。 (2) 构建过程与计算步骤：1. 计算根节点整体信息熵： 14个样本，7正7负。$H(D) = -\frac{7}{14}\log_2\frac{7}{14} \times 2 = \mathbf{1.0}$2. 计算第一层各属性信息增益： 价格(Price)： 低价(4正0负): $H=0$ 高价(2正3负): $H= -\frac{2}{5}\log_2\frac{2}{5} - \frac{3}{5}\log_2\frac{3}{5} \approx 0.971$ 中价(1正4负): $H= -\frac{1}{5}\log_2\frac{1}{5} - \frac{4}{5}\log_2\frac{4}{5} \approx 0.722$ $Gain(Price) = 1.0 - (\frac{4}{14}\times 0 + \frac{5}{14}\times 0.971 + \frac{5}{14}\times 0.722) \approx \mathbf{0.395}$ 续航时间(Bat) / 摄影性能(Cam)： 均为 (5正3负) 和 (2正4负)。 $H(5,3) = 0.954$； $H(2,4) = 0.918$ $Gain(Bat) = Gain(Cam) = 1.0 - (\frac{8}{14}\times 0.954 + \frac{6}{14}\times 0.918) \approx \mathbf{0.062}$ 结论： 根节点选择“价格”。 3. 子节点划分与完整树： 低价分支：纯净（全是），变为叶节点。 高价分支子集：观察表中数据，按续航划分，长$\rightarrow$是，短$\rightarrow$否，实现纯净。 中价分支子集：观察表中数据，按摄影划分，强$\rightarrow$是，弱$\rightarrow$否，实现纯净。 决策树图形： 12345678910 [ 价格 ] / | \ / | \ 低价 高价 中价 / | \(是) [ 续航 ] [ 摄影 ] / \ / \ 长 短 强 弱 / \ / \ (是) (否) (是) (否) (3) 缺陷与解决方法： 缺陷： ID3 算法偏好选择取值分支极多的属性（如身份证号），这极易导致模型过拟合。 解决方法（防过拟合）： ① 引入预剪枝（Pre-pruning），在树生长过程中提前停止；② 引入后剪枝（Post-pruning），生成完整树后自底向上裁剪分支；③ 使用 C4.5 算法，改用信息增益率来惩罚分支过多的属性。 第六题：K-Means 聚类(1) 流程与准则函数： 流程： ① 随机初始化 $K$ 个簇中心；② 计算所有样本到各中心的距离，将样本划分到距离最近的簇；③ 重新计算每个簇内所有样本的均值，更新为新的中心；④ 重复②③，直到中心不再变化。 准则函数： 最小化平方误差和 (SSE)。 $J = \sum_{k=1}^K \sum_{x \in C_k} ||x - \mu_k||^2$ (2) 应用与问题： 应用场景： 用户画像分群、图像颜色量化压缩。 问题： ① 极度依赖初始中心的选择，容易陷入局部最优；② 容易受到异常值（离群点）的干扰。 改进方法： 采用 K-Means++ 算法改进初始化策略，使得初始中心点之间的距离尽可能远。 第七题：集成学习(1) Bagging 流程与结合策略： 流程： 采用自助采样法（Bootstrap）有放回地从原始数据集中抽取多个不同的训练子集；基于这些子集，并行且独立地训练出多个基学习器；最后将基学习器的结果进行结合。 结合策略： 在分类任务中，通常采用简单多数表决法；在回归任务中，通常采用简单平均法。 (2) 随机森林原理： 随机森林是以决策树为基学习器的 Bagging 扩展。 它的特殊机制在于引入了“特征随机性”（随机子空间）：在决策树的每个节点分裂时，不考察所有的特征，而是随机抽取一个包含部分特征的子集（如 $\sqrt{d}$ 个），在此子集中寻找最优切分点。这进一步降低了各决策树之间的相关性，提升了泛化能力。 第八题：BP 神经网络推导根据链式求导法则推导：(1) 输出层权值 $w_{km}$ 更新： $$\frac{\partial E_n}{\partial w_{km}} = \frac{\partial E_n}{\partial y_{nk}} \frac{\partial y_{nk}}{\partial z_{nk}} \frac{\partial z_{nk}}{\partial w_{km}} = \mathbf{2 (y_{nk} - t_{nk}) \cdot \sigma’(z_{nk}) \cdot h_m}$$ 令局部梯度 $\delta_k = 2(y_{nk} - t_{nk})\sigma’(z_{nk})$，则更新公式为： $$w_{km} \leftarrow w_{km} - \eta \cdot \delta_k \cdot h_m$$ (2) 隐藏层权值 $w_{md}$ 更新：需要对所有受到隐藏层神经元 $m$ 影响的输出层神经元 $k$ 进行求和： $$\frac{\partial E_n}{\partial w_{md}} = \left( \sum_{k=1}^K \frac{\partial E_n}{\partial z_{nk}} \frac{\partial z_{nk}}{\partial h_{m}} \right) \frac{\partial h_{m}}{\partial z_{nm}} \frac{\partial z_{nm}}{\partial w_{md}}$$ $$= \mathbf{\left( \sum_{k=1}^K \delta_k \cdot w_{km} \right) \cdot h’(z_{nm}) \cdot x_{nd}}$$ 令局部梯度 $\delta_m = \left( \sum_k \delta_k w_{km} \right) h’(z_{nm})$，则更新公式为： $$w_{md} \leftarrow w_{md} - \eta \cdot \delta_m \cdot x_{nd}$$ 第九题：开放性论述（大模型技术）(1) 关键底层技术：大模型（如 ChatGPT、Sora）的核心建立在 Transformer 架构之上，利用其强大的注意力机制进行序列建模。主要依赖大规模生成式预训练（自回归生成或扩散模型），并在后处理阶段辅以人类反馈强化学习（RLHF）以对齐人类意图。 (2) 面临的技术与工程挑战： 算力与数据壁垒： 模型的训练和推理需要极其庞大的 GPU 集群算力；同时，高质量的人类标注数据和多模态对齐数据正面临枯竭的风险。 “黑盒”与幻觉问题： 大模型缺乏真实的物理规律和逻辑因果知识，极易产生一本正经胡说八道的“幻觉”，且其决策过程不可解释，难以在严肃医疗、自动驾驶等容错率低的领域落地。 (3) 潜在的社会伦理风险： 深度伪造与诈骗： 逼真的音视频生成能力容易被恶意利用，制造虚假新闻冲击社会信任。 版权与隐私纠纷： 训练数据往往包含未经授权的版权素材或用户隐私。 劳动力冲击： 强大的泛化能力可能导致客服、画师、初级程序员等岗位面临结构性失业危机。

六、四个单元中架构设计思维的演进第一单元让我建立了“语法结构即对象结构”的意识。表达式展开与化简看似是字符串处理，但如果一直依赖字符串拼接，后续加入自定义函数、指数函数、选择表达式和求导时会非常难维护。更好的做法是把表达式拆成词法分析、语法分析、表达式树或项/因子的层次结构，让新增语法尽量变成新增节点或新增规则，而不是修改所有旧逻辑。 第二单元让我认识到“对象之间的协作比单个对象更重要”。多线程电梯系统中，正确性不仅取决于电梯类怎么写，还取决于输入线程、调度器、请求队列、电梯线程之间如何通信。这个单元让我开始关注线程安全、生产者—消费者模型、共享队列、结束条件和时间顺序。架构设计不再只是类的静态划分，还包括对象生命周期和并发协作方式。 第三单元的规格化设计改变了我看代码的方式。JML 规格把方法的前置条件、后置条件、副作用和异常情况都写得很清楚，这要求我先理解“这个方法承诺了什么”，再选择数据结构和算法。第 9–11 次作业中，在线视频平台从用户关注和视频互动扩展到硬币经济、评论、粉丝勋章、推荐系统等功能。我的实现逐渐从简单的 Network、User、Video 三类，扩展出 SocialGraph 和 RecommendationEngine 等辅助类，以避免 Network 过度膨胀。这个过程让我意识到，规格不是代码的负担，而是帮助划定责任边界的工具。 第四单元则把架构设计推进到“模型先行”。我不再只是根据题目直接补类，而是先从类图中确定稳定领域对象，再用状态图确认对象行为，用顺序图检查对象协作。尤其是在图书馆系统中，图书副本状态、读者信用状态、预约状态和日期约束相互影响，如果没有模型，很容易在迭代中把逻辑写散。正向建模让我更习惯于先问：这个状态属于哪个对象？这个变化由谁触发？这个关联能否在代码中追踪？ 总体来看，我的架构思维经历了四个阶段：从字符串过程处理，到对象封装；从对象封装，到并发协作；从并发协作，到规格驱动；从规格驱动，到模型驱动。最后我对“面向对象”的理解也更完整：面向对象不是简单地多建几个类，而是让类的职责、对象状态、交互关系和需求变化保持一致。 七、四个单元中测试思维的演进第一单元的测试重点是表达式正确性。最开始我会手写一些样例，后来逐渐意识到表达式问题适合用随机测试和对拍测试：随机生成表达式，分别用自己的程序和可靠的数学化简/求值方式进行比较。由于输出形式不唯一，测试时不能只比较字符串，而要比较在多个变量取值下的语义等价。 第二单元的测试重点是并发时序。电梯作业不是单纯比较最终结果，还要检查过程是否符合时间、载重、开关门和接送规则。因此测试思维从“输出对不对”变成“日志过程是否合法”。我需要构造高峰请求、跨楼层请求、临时检修、双轿厢等场景，并关注死锁、线程提前结束、请求丢失、重复接送等问题。 第三单元的测试重点是规格覆盖。JML 方法的异常条件非常明确，所以我开始按正常路径、异常路径和边界值拆分测试。例如用户不存在、视频不存在、重复关注、自关注、未观看就点赞、硬币不足、评论编号重复等情况，都需要与规格逐条对应。这个单元也让我更加重视数据结构性能测试，因为规格正确但复杂度过高仍然可能超时。代码中对最短路缓存、贡献者 O(1) 维护、评论清理 O(N) 重建、推荐候选堆等优化，都是在正确性之外对性能测试的回应。 第四单元的测试重点是场景一致性和状态追踪。图书馆系统的很多错误不会在单个请求中暴露，而会在跨日期、跨状态的长序列中出现。例如预约到期日、开馆和闭馆整理时机、阅览室未归还扣分、逾期扣分是否重复、续借是否允许、精品书架和普通书架之间的切换，都需要通过连续场景测试。相比前三个单元，第四单元更适合从状态图和顺序图反推测试用例：每条状态转移至少构造一次，每个拒绝条件至少覆盖一次，每个日期边界单独测试。 因此，我的测试思维也经历了变化：从样例驱动，到随机与对拍；从结果验证，到过程验证；从功能覆盖，到规格覆盖；最后到模型驱动的场景覆盖。测试不再是写完代码后的补救，而是反过来帮助我检查架构是否清晰。 八、课程收获这门课给我的最大收获，是让我真正理解了“复杂度管理”在软件开发中的意义。很多时候程序失败并不是因为某一行代码写错，而是因为一开始没有把责任边界设计好。第一单元教会我用结构化对象处理表达式，第二单元教会我在并发系统中处理对象协作，第三单元教会我尊重规格和契约，第四单元教会我用 UML 模型指导开发并追踪实现。 我也更加理解了迭代开发中的可扩展性。一个设计在第一次作业中能通过，不代表它能承受第二、第三次迭代。真正好的设计应该允许需求增长时以局部修改为主，而不是每次都推翻重来。第四单元的图书馆系统就是一个典型例子：当新增精品书架、评分、阅读、信用分、借阅期限和续借时，如果原本已经把图书、读者、预约、仓库、场所和管理器分清楚，新增需求就可以落到相对自然的位置。 最后，我对大模型辅助编程也有了更理性的认识。大模型适合帮助梳理需求、生成候选类、检查追踪关系、构造测试场景，但最终设计质量仍然取决于我是否理解题面、是否能判断职责边界、是否能用测试验证模型。它可以提升建模效率，却不能替代对系统本身的思考。 经过四个单元，我从“为了通过评测写代码”逐渐转向“为了控制复杂度做设计”。这也是我认为 OO 课程最有价值的地方：它不只是训练 Java 语法和具体算法，而是训练一种面对复杂需求时仍然保持结构清晰、责任明确、可验证、可迭代的软件设计思维。

匹配误写成正则匹配或非重叠匹配。 第三次作业测试 recommend_Nth_up 时，我的思路是把排序规则独立出来。测试中需要覆盖非法 rank、无视频、候选 UP 主不足、分数相同按 ID 取小、排除自己和已经关注的人、连续调用不改变用户状态等场景。推荐类方法看上去只是“返回一个 ID”，但它隐含了候选集合筛选、打分、排序、异常和纯净性多个方面，任何一个环节漏测都可能放过错误实现。 总结下来，JUnit 测试最有效的模式有三点：第一，测试 oracle 要尽量独立于正式实现，避免复制同一个 bug；第二，要对调用前后的状态拍快照，尤其是纯查询方法和只允许局部修改的方法；第三，边界数据比大规模随机数据更容易发现规格理解错误，例如空集合、重复 ID、相同分数、重复转发、重叠字符串、并列最大值和 tie-break。 三、三次作业的迭代过程1. 第一次作业：社交网络与基础视频推送第一次作业的主要任务是实现 User、Network、Video 三个类，维护用户、视频、关注关系、粉丝关系、接收视频列表，以及互相关注数、最短路径等查询。 我的实现中，Network 维护了 users 和 videos 两个 HashMap，并额外维护 outEdges 和 inEdges 两张邻接表，分别表示“某人关注了哪些人”和“某人被哪些人关注”。这样做的原因是，关注图既要支持关注/取消关注，也要支持最短路查询和互相关注统计。如果完全依赖 User 内部容器反复遍历，会在高频查询时产生不必要的复杂度。 对于 queryMutualFollowingSum，我没有在每次查询时重新双重循环统计，而是在 followUser 和 unfollowUser 中动态维护 mutualFollowingSum。当新建边 id1 -> id2 时，如果反向边 id2 -> id1 已经存在，则互关数加一；删除边时同理减一。因此查询可以做到 O(1)。对于 queryShortestPath，我使用 BFS，在有向关注图上查找最短路径。 User 中使用 HashMap 管理 following 和 followers，用 LinkedList 管理收到的视频列表，便于新上传视频头插；同时维护年龄段计数数组 ageSegments，使粉丝年龄比例查询不必每次遍历粉丝集合。 2. watchedVideoIds、likedVideoIds、medalUpIds 和 contributorMap。对于最佳贡献者，我没有每次查询都遍历 contributorMap，而是在每次收到投币时维护 bestContributorId 和 maxContribution，并在贡献值相同的时候按较小 ID 更新。 Video 新增了分区类型、播放量、点赞数、转发数、投币数，以及评论 ID 和评论内容两个平行 ArrayList。为了快速判断评论 ID 是否重复，我额外维护 commentIdSet。评论清理使用迭代器同步删除 ID 和内容，并返回删除数量和被删评论中关键字最大出现次数。 此外，第二次开始我明显感受到“规格正确”和“复杂度可接受”是两件事。比如视频分区查询如果每次遍历所有视频也能写对，但在强测中可能超时，所以我维护了 typeVideos。最短路查询也增加了缓存，但所有会改变关注图的操作都会清空缓存，避免读到过期结果。最长年龄下降序列则使用 DFS + DP 缓存，并在可能改变结果的图操作后失效。 3. 第三次作业：智能推荐与结构拆分第三次作业继续扩展系统，加入推荐视频、推荐第 N 个 UP 主、查询最有影响力 UP 主、查询用户画像、查询全局最佳贡献者等功能。此时如果继续把所有逻辑塞进 Network，类会变得过长且难以定位问题。因此我把代码拆分为三个主要部分：Network 作为接口门面，负责异常检查和对外方法；SocialGraph 负责关注图、互关数、最短路和最长下降序列；RecommendationEngine 负责推荐和贡献者统计。 在 User 中，我新增了 typeCounts 来记录用户在各分区观看的视频数量，并维护用户上传的视频和分区影响力。观看视频时，不仅要从 receivedVideos 中删除该视频，还要加入观看历史，并增加对应分区的观看计数。推荐视频时，视频得分可以理解为视频热度与用户对该分区兴趣的乘积；推荐 UP 主时，则根据用户兴趣和 UP 主分区影响力进行加权求和。 性能方面，第三次我做了两点优化。第一，UP 主影响力不再每次通过遍历其所有上传视频求和，而是在观看、点赞、取消点赞、投币、转发等热度变化点增量维护。第二，recommendNthUp 不再对所有候选人完整排序，而是用大小为 rank 的优先队列保留当前前 rank 名，把复杂度从全排序降到和 rank 相关的堆维护。这也让我认识到，JML 中的 \sum、\max、排序式描述往往表达的是数学结果，而不是要求实现必须用同样朴素的枚举方式。 四、如何发现迭代中的方法和容器变化我主要使用三步法发现变化。 第一步是看指导书和接口中的 Modify、新增方法和构造方法变化。例如第二次 Video 构造方法新增 type 参数，User 新增 coins、watchedVideos、likedVideos、medals、contributors、contributions 等状态；第三次 User 又新增 typeCounts 和 videos，Network 新增智能推荐相关方法。 第二步是看 JML 中新增的 ensures、assignable 和异常规格。如果某个后置条件开始引用一个新的状态量，就说明实现中需要新增容器或缓存。例如 hasWatchedVideo、hasLikedVideo、containsComment、getInterest、getInfluence 等方法都对应着新的可观察状态。 第三步是用编译错误和回归测试辅助确认。方法签名变化会直接导致编译失败；行为变化则要靠旧测试回归和新增测试发现。例如第二次保留第一次关注图功能，第三次保留前两次所有指令，这要求新增功能不能破坏原有容器不变式。 五、如何发现性能瓶颈说实话，其实写到那个for自己就能意识到这里性能可能有点问题，但是严谨来说，我的性能瓶颈排查主要来自两个方面：规格复杂度和调用频率。 从规格复杂度看，只要 JML 中出现嵌套量词、全局 \sum、最大值、排序、路径存在性，就要警惕直接翻译造成高复杂度。例如互相关注数如果每次查询都双重遍历用户是 O(n²)，最短路径如果每次都 BFS 在大量重复查询下可能很慢，影响力如果每次都遍历所有视频也会在推荐场景中被放大。 从调用频率看，强测通常会把查询类指令大量重复调用，所以适合用动态维护或缓存。我的处理方式是：互关数、年龄段人数、最佳贡献者、UP 主影响力采用增量维护；最短路径和最长下降序列采用缓存，但在图变化时失效；分区视频集合单独维护，避免每次查询遍历所有视频；推荐第 N 个 UP 主使用优先队列，避免全量排序。 这也带来一个原则：缓存不能破坏规格。对于纯查询或只允许修改特定对象的方法，即使内部用了缓存，也必须确保不会改变任何外部可观察状态，并且在相关状态变化时及时失效。 六、Bug 与原因分析本单元的 Bug 分析可以分为三类：提交前自测发现的问题、互测中发现的典型实现问题，以及性能风险与复杂度问题。 6.1 提交前自测发现的问题 对象相等语义理解错误 第一次作业早期版本中，Video.equals 同时比较 id 和 uploaderId。 修正思路：视频在网络中的唯一身份由 videoId 决定，规格容器的不变式和方法如 containsVideo 都围绕 ID 判断。最终 Video.equals 只比较 getId()。 异常参数混淆 第二次作业中，购买勋章时如果用户已经拥有该 UP 主勋章，曾错误抛出 DuplicateMedalException(userId, videoId)。 修正思路：勋章绑定 UP 主而非视频，正确参数应为 DuplicateMedalException(userId, upId)。 评论清理边界匹配错误 在 clean_spam_comments 测试中，字面关键字匹配和非重叠匹配理解不当，导致 a.b、a*b、ababa 等边界用例出错。 修正思路：按规格要求的字面匹配实现 oracle，确保重叠出现的关键字被正确统计和删除。 异常顺序与事务一致性 投币、购买勋章等方法中，若在检查异常前已修改部分对象状态，可能导致状态不一致。 修正思路：先完成所有异常检查，再统一更新多个对象状态，确保事务一致性。 6.2 互测中发现的典型问题 hw9 双向 BFS 写错 部分实现没有正确维护双向搜索的前后关系，导致最短路径查询返回错误或陷入死循环。 hw11 UpRecommender 排序溢出 有实现使用 return user1.getId() - user2.getId(); 比较用户 ID，由于 int 溢出，排序可能出错。 特殊标识冲突 有实现用 -1 作为标识值，但 -1 本身也是合法用户 ID，导致逻辑异常。 异常输出顺序错误 部分实现能抛出正确异常，但输出顺序不符合要求，影响测试判定。 6.3 性能问题与复杂度风险 重复遍历容器 某些实现对视频列表、关注图、贡献者映射每次查询都全量遍历，容易在强测中超时。 缓存与增量更新不当 UP 主影响力、互关数、年龄段统计等若不增量维护，频繁查询时复杂度被放大。 排序与全量扫描 推荐第 N 个 UP 主或推荐视频，如果对所有候选完整排序而不是使用优先队列或部分排序，复杂度随用户数量急剧增加。 最长下降序列和最短路径缓存 缓存若未在关注图变化时失效，可能返回过期结果，违反纯查询或副作用约束。 七、大模型使用体会本单元我更适合把大模型当作“辅助阅读规格和生成测试思路”的工具，而不是直接生成最终代码的工具。它的优势在于可以快速把长 JML 翻译成自然语言、列出可能的边界条件、提醒某个方法需要检查哪些副作用，也可以帮助生成 JUnit 用例框架。 但大模型的风险也很明显。第一，它容易给出“看起来正确”的朴素实现，比如按 JML 的数学表达直接遍历所有对象，却忽略强测中的性能压力。第二，它不一定知道课程官方包中异常参数、输出格式和扩展语义的细节。第三，它可能忽视容器架构，导致新增功能时不断在原类中堆字段和方法，而不是抽象出 SocialGraph、RecommendationEngine 这样的组件。 因此我认为比较安全的使用方式是：让大模型帮助列测试清单、解释某段 JML、对照 requires/ensures/assignable 检查遗漏；最终实现仍然要自己结合官方接口、复杂度和评测限制判断。对于单元测试，可以让大模型先列边界场景，再由自己写独立 oracle 和状态快照检查。 另外，大模型对于时间复杂度的优化很有用，可以严防TLE。 八、JML“击鼓传花”研讨课感悟本次研讨课的游戏名为“规格传声筒”，规则类似“击鼓传花”或“传话游戏”。每组 6 到 7 人，每个人先写一个带有边界条件的初始方法签名与业务场景，然后依次经历 自然语言规格 → JML 规格 → 自然语言规格 → JML 规格 → 自然语言规格 → 最终 JML 规格 的多轮环状传递。传递过程中禁止使用 AI，所有回合结束后，再对比第一轮的初始自然语言规格和最后一轮的 JML 规格是否逻辑等价。评分重点包括逻辑同构、边界遗失、过度设计和业务畸变等。规格传声筒 这次活动让我非常直观地感受到，规格在传递过程中很容易发生“语义漂移”。最开始的自然语言需求可能只是一个很小的方法，例如查询集合、更新状态、处理图关系或统计某类对象，但经过几轮 NL 和 JML 的相互翻译后，原来的边界条件、异常行为、修改范围甚至业务目标都有可能被改变。比如原本要求处理 null、空集合或重复元素，传到后面可能这些边界就消失了；原本只是查询方法，后面可能漏写 assignable \nothing；原本有异常行为，后面可能只剩下正常行为；原本的 tie-break 规则，也可能在传递中被忽略。 我认为这个活动最有意义的地方在于，它暴露了自然语言和形式化规格之间的差距。自然语言的优点是易读，但很容易产生歧义；JML 的优点是精确，但写规格的人如果没有完全理解业务含义，也会把错误理解“形式化”下来。一旦错误被写进 JML，后续实现者往往会认为它就是正确契约，从而导致实现偏离最初需求。因此，形式化并不等于天然正确，形式化之前必须先保证需求理解正确。 游戏中的几类扣分点也很贴近真实开发。所谓“边界遗失”，对应实际项目中常见的空容器、非法输入、重复对象、不可达路径等问题；“过度设计”则对应实现者或规格编写者加入了原需求没有要求的限制，例如额外限制数组长度、ID 范围或调用顺序；“业务畸变”更严重，意味着方法的核心功能在多次转述后已经变成了另一个问题。这些问题在本单元三次作业中也经常出现，例如异常顺序写错、用非法标识值代替合法 ID、把推荐排序规则理解错，或者忘记某个方法是纯查询。 这次研讨课也让我重新理解了 JML 在团队协作中的价值。JML 不只是为了通过评测，也不是为了把代码写得更“形式化”，它真正的作用是帮助团队成员共享同一个契约。一个方法到底允许修改哪些对象、什么时候抛异常、返回值和旧状态有什么关系、并列情况下如何排序，这些内容如果只靠口头说明，很容易在多人协作中被误解；如果用 JML 明确下来，后续写代码、写测试和做评审时就都有了统一依据。 同时，我也认识到，团队合作中不能只把 JML 当作最终结果，而应该把规格编写过程本身纳入评审。比较合理的流程应该是：先由需求提出者写出自然语言说明，明确正常行为、异常行为、边界条件和副作用；再由规格编写者写出 JML；然后由其他成员对照自然语言和 JML 检查是否等价。尤其要重点检查 requires、ensures、assignable、signals、\old 和量词表达式是否遗漏或过度约束。只有经过这种双向检查，JML 才能真正减少沟通成本，而不是制造新的误解。 从本单元作业的角度看，“规格传声筒”也提醒我，写测试时不能只测试自己脑中的需求，而要测试规格中真正写出来的契约。如果规格中要求纯方法，就要检查调用前后状态不变；如果规格中要求异常时 assignable \nothing，就要检查抛异常后对象没有被部分修改；如果规格中有排序规则，就要专门构造并列情况；如果规格中有边界条件，就要测试空集合、重复元素、不可达路径、非法参数等情况。也就是说，测试本身也是对规格理解是否准确的一次验证。 总的来说，这次研讨课让我意识到，软件开发中的很多 bug 并不是因为不会写代码，而是因为需求在传递、翻译和实现过程中被悄悄改变了。JML 的价值就在于尽量压缩这种“我以为”的空间，让需求、规格、实现和测试围绕同一个契约展开。以后在多人组队编程中，我会更加重视规格文档的唯一性、边界条件的显式记录、异常行为的完整描述，以及每次需求修改后的同步评审。 九、总结Unit3 让我把面向对象设计从“类和方法的组织”推进到“契约、状态和复杂度的组织”。第一次作业让我熟悉了用规格描述社交图；第二次作业让我意识到事务性操作和副作用控制的重要性；第三次作业则让我开始主动拆分模块、维护缓存并从复杂度角度理解 JML。 最终我对规格驱动开发的理解是：JML 给出的是程序外部可观察行为的数学契约，真正的实现既要满足这个契约，也要在数据结构和复杂度上适应评测规模。好的实现不是简单把 JML 翻译成循环，而是在不改变规格语义的前提下，选择合适的容器、缓存和模块划分。好的测试也不是只看输出，而是把前置条件、后置条件、副作用和异常路径都纳入验证。这个单元之后，我会更加重视在编码前先读规格、在迭代中维护变化表、在提交前用测试检查契约完整性。

所谓“脏页”，是指在某一段特定时间内，被应用程序写入或修改过的内存页面。掌握脏页记录意味着系统能精确追踪内存的变动，这种机制在一些领域有所应用：在云计算场景中，虚拟机热迁移时，它用于获取迁移期间的内存修改，并同步至目标机器；而在后续的文件系统实验中，它可以用于识别缓存中的修改内容，确保在关闭文件时能准确地将数据持久化到磁盘。 在本题目中，你需要结合 Lab4 课下实验中的系统调用机制、写时复制机制、页写入异常等知识点，在 MOS 中实现脏页记录功能。 要求实现的功能分为以下三个步骤： 用户进程首先使用“启用脏页追踪”的系统调用，指定自身地址空间内的一段地址范围启用脏页追踪，将其中的可写页面打上 PTE_LOG 的追踪标志位，同时去除其 PTE_D 可写标志位。这样，当用户进程尝试写入被追踪的页面时，将引起页写入异常，使得内核能记录脏页；对于只读或者未映射的页面，则不进行操作； 当用户进程写入追踪页时，将发生页写入异常，陷入内核态。内核在对应用户进程的脏页队列中记录对应页面的虚拟地址，并去掉 PTE_LOG 追踪标志位，恢复该页的可写标志位。这样，当从内核态返回用户进程，重新执行写入指令时，相应的页已经是可写状态，写入指令可成功执行； 显然，内核为每个进程维护的脏页队列大小是有限的，当脏页队列满时，类似 Lab4 课下实现的写时复制机制，内核将控制权交由用户态的处理代码，并同时将完整的脏页记录传递给该处理代码，处理代码可对脏页记录进行转储等操作，处理完毕后使用系统调用从处理逻辑回到异常现场。注意：为避免用户态处理代码访问其他追踪页时引发嵌套异常，内核需将完整的脏页记录复制到用户态的异常栈上，供用户进程访问。复制完成后，内核将清空该进程的脏页队列。 Extra：题面很长，但核心是“把写操作变成一次可记录的异常”Lab4 Extra 是脏页追踪。这个题比 Exam 大很多，题面中一共给了很多需要填的位置，但它的核心机制其实可以概括成一句话： 开启追踪时，先把可写页改成“不可写但带 PTE_LOG 标记”；用户一写这个页，就触发 TLB Mod；内核记录这次写入，再把页面恢复可写。 按照这个思路，整道题可以拆成三条线。 第一条线是进程控制块。每个进程都要知道自己是否正在开启脏页追踪、当前记录了哪些脏页、用户态处理函数入口在哪里。所以要在 Env 里加： 123u_int log_enabled;struct DirtyPageQueue log_queue;u_long log_entry; 同步块的设置与锁的选择在多线程环境中，锁的粒度与对象的选择直接决定了系统的正确性与吞吐量。在三次作业的演进中，我的锁机制也经历了由简入繁的过程。 1. 锁的对象与粒度演进 HW5（基础阶段）：由于输入指令已经指定了电梯，系统仅需实现基础的生产者-消费者模型。我将锁直接加在 MainQueue 和 SubQueue 内部的集合操作方法上（如 addRequest 和
